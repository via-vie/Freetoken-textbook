1.1 从一次真实困惑开始

假设模型共有 100 GiB 参数，但当前 GPU 只能给权重留下 20 GiB。我们听说 MoE 每步只激活少数专家，于是产生一个直觉：既然只用一小部分，直接加载这一小部分不就可以了吗？问题在于，这一层会选哪些专家，要等前一层算出 hidden states、再经过 router 才知道。下一步、下一请求还可能换一批。没有被当前 token 用到的专家，也不能永远丢掉。 FreeToken 要解决的就是这类运行时问题。它读取已经训练好的权重，把较大的专家集合保存在主存，根据执行阶段把需要的权重送到 GPU，或者直接让 CPU 计算部分专家。这里“free”不意味着数学运算或内存访问没有成本；学习这套引擎，关键是看清成本被放在哪里、何时发生、如何与其他工作重叠。 本书以官方 FlashML-org/FreeToken 的固定提交为准。它也有稠密模型、不同注意力、量化、多模态和多卡支持。为了先抓住主干，我们以单卡、文本、MoE、普通因果注意力讲完整请求，随后再把扩展分支接回地图。没有要求你先装好上百 GiB 权重。

停一下，自己推 · 如果增加 GPU 专家 slots，能保证每条请求的 KV 容量也增加吗？

不能。二者竞争显存。专家 miss 可能减少，但留给 KV、状态与运行时的容量可能减少。必须联合结账。

停一下，自己推 · 推理引擎会在每次回答时重新训练 router 吗？

普通推理不会。router 的参数来自 checkpoint；每次计算新的路由结果，改变的是本步选中专家与缓存驻留状态。

2.1 把模型缩小到能检查

这里取 N=1、D=4、E=8、top-k=2、FFN 中间维度 F=6。输入 x=[1,0,−1,2]。E 指每层可选专家数，不是所有层的专家总数。一个 route 是“一个 token 选择某个专家并带一个权重”；两个 token 都选择专家 3，就有两条 route，却只有一个需要搬运的唯一专家。 教学 router 矩阵 R 为 4×8。我们按行向量约定计算 z=xR，得到 [0.300,0.500,−0.300,1.100,−0.500,0.100,−0.300,0.600]。例如第 3 号专家（从 0 编号）的 logit 为 1×0.4+0×0−1×(−0.1)+2×0.3=1.1。 softmax 先把 logits 转为 8 个概率；选择最大的两个，对应专家 3、7。我们规定选中后再归一化，因此权重分别为 0.622459… 与 0.377541…。这等价于在这两个选中 logits 上做 softmax。本例选择这一规则是为了算清楚；真实模型还可能有 sigmoid、分组选择、bias、缩放或共享专家，必须看具体 router。

2.2 专家内部没有魔法

每个专家都有 Wg、Wu、Wd。按本书的行向量记法，Wg 和 Wu 是 4×6，Wd 是 6×4。先求 g=xWg、u=xWu，再求 a=SiLU(g)⊙u，最后求 ye=aWd。SiLU(t)=t/(1+exp(−t))，⊙ 表示对应元素相乘。 为了让你复算任意元素，所有权重都有定义。下列 i、j、e 都从 0 编号；脚本生成完整矩阵，不依赖随机种子。

Wg[e,i,j] = (e+1)*(i+1)*(j+1)/100
Wu[e,i,j] = (i-j+e+1)/20
Wd[e,i,j] = (j+1)*(i+1)/(50*(e+1))

专家 3 的 g=[0.240,0.480,0.720,0.960,1.200,1.440]，u=[0.600,0.500,0.400,0.300,0.200,0.100]。它的第一个中间元素是 SiLU(0.24)×0.6≈0.081。六个中间元素乘 Wd 后得到 y3≈[0.017,0.034,0.051,0.068]。专家 7 得到 y7≈[0.060,0.119,0.179,0.238]。 最终 y=0.622459…×y3+0.377541…×y7≈[0.033,0.066,0.099,0.132]。显示时保留约三位小数，后续计算始终使用完整浮点值。真实 PyTorch 权重常以输出维在前保存，kernel 还会转置或打包；矩阵物理布局不能直接套用本段的教学方向。

3.2 把进程和对象分开画


launch_server 先 parse_args，必要时解析 GPU 标识，再构造 start_subprocess 回调交给 run_api_server。回调使用 spawn，为每个 TP rank 启动 Scheduler 进程，另启动 detokenizer 和配置数量的 tokenizer workers。默认参数还会影响 tokenizer 链接方式，不能把图中的一个功能框机械地理解为永远只有一个固定进程。 单 A100 对应 TP size=1，模型执行后端只有一个 rank。FrontendManager 在 API 服务侧负责 uid、消息发送与结果队列；Scheduler 进程里包含 Scheduler 对象和 Engine 对象，后者绑定 GPU、加载模型、建立缓存与图。一个 Engine 对象不等于一个单独的 Engine 进程。




边界传递的东西这一步不应混淆的状态


HTTP → 前端JSON、连接、采样设置网络生命周期与 GPU 生命周期不同


前端 → tokenizerTokenizeMsg、uid、模板参数原始 messages 还不是模型 ids


tokenizer → schedulerUserMsg，含 ids 与采样参数uid 用于把结果送回原请求


scheduler → detokenizer → 前端next_token、finished、错误/统计模型 token 与文本 delta 不同

4.3 pinned memory 解决什么

   66  
   67      ``budget_bytes`` is the net pool for MoE cache + KV cache (caller already subtracted
   68      weights + fixed_cache_size; the (1-memory_ratio) remainder is the graph headroom).
   69      Experts greedily fill the budget after reserving ``kv_reserve_pages`` for KV, clamped
   70      to ``[floor, min(total_experts, max_slots)]`` (floor is ``2*num_experts`` when prefill

假设请求变长，预留 KV 从 7 GiB 提到 11 GiB，其余不变，专家预算从 20 降到 16 GiB，按同一教学 slot 可放 128 个。专家 miss 率可能升高，但更长上下文得以容纳。反之，强行保持 160 slots 可能让队列无法被接纳。 双缓冲需要容得下两层专家的暂存视图；CPU MoE 策略的 GPU 预留也不能简单理解为零专家空间。初始化配置会根据策略调整。auto 是一个规则集合，最终日志里的 Resolved config 比你只看命令行中写的 auto 更接近真实执行。

8.2 一次 Attention 的形状


为了手算，取双头 h=2、每头 d=2、D=4，暂用 MHA。Hnorm[3,4] 分别乘 WQ/WK/WV[4,4]，得到 Q/K/V[3,4]，再看成 [3,2,2]。每头 QKᵀ 得 [3,3] 分数，缩放后施加因果 mask；位置 i 只能读不晚于 i 的位置。每行 softmax 后乘 V，得到每头 [3,2]，拼接并输出投影回 [3,4]。 真实 GQA 中 Q head 数可大于 KV head 数，K/V 形状按 KV heads 计算，多个 Q heads 共享一组 K/V。RoPE 用 positions 旋转 Q、K；它不把 token id 当位置，也不替代因果 mask。Q/K norm、SWA 和 sparse attention 是否存在由模型与 backend 配置共同决定。

11.1 先把集合写清楚


令 H 为命中的唯一专家，M 为缺失的唯一专家。把 M 分成 F 与 C：F 被搬到 GPU，C 在 CPU 原地计算。GPU 最终处理 H∪F，CPU 处理 C。它们必须不重不漏。q=|F|，m=|M|；别把 m 错写成 batch_size×top_k，那是 route 数上限，去重后可能小很多。 为什么要保留 fill？本步 CPU 可以算完一个缺失专家，但若它以后常被选中，搬到 GPU 会让后续命中。反过来，一口气填满所有 miss 又可能被 PCIe 限制。因此这是本步关键路径与后续驻留的共同问题；本章的带宽模型只解决其中的时间分工。


11.2 用同一单位推时间


先采用简化模型：单专家 S 字节；有效 H2D 带宽 BP；主存侧总有效带宽 BH，且 BH>BP。若 DMA 与 CPU 争用主存，简化地把并发 CPU 剩余带宽记为 BH−BP。于是 fill 时间约 qS/BP，CPU 时间约 (m−q)S/(BH−BP)。两边重叠时较慢的一边决定结束时刻，因此应比较 max，而不是把两个时间相加。 令两项相等，q(BH−BP)=(m−q)BP，得到 q*=mBP/BH。它依赖一系列假设：均匀专家大小、可重叠、忽略启动固定成本、CPU 计算可用带宽描述。若 BH≤BP，这个剩余带宽写法不再适用；也不应拿厂商标称值代替本机有效值。 教学例子 m=8、S=64 MiB、BP=20 GB/s、BH=80 GB/s，q*=2。fill 两专家约 6.711 ms；CPU 六专家在 60 GB/s 下也约 6.711 ms。表中 GB/s 是十进制字节带宽，MiB 是 2²⁰ 字节，换算不能混掉。

每个 token 每层都临时创建线程的代价太高。CpuMoeExecutor 初始化原生扩展和线程池，并让输入、输出、描述符与信号具有稳定地址。CPU 指令集、线程数、亲和性和 NUMA 会影响有效吞吐；A100 并不能告诉我们配套 CPU 的主存带宽。 当前实现根据探测结果使用 flag publish/signal/wait、kernel I/O 或 host function 等路径。CUDA Graph 兼容性取决于这一协议是否可重放；探测不支持时，代码可能要求禁用图，而不是默默产生旧结果。Engine 每次 forward 还检查 executor 健康状态，避免 CPU 协调线程失效却继续用陈旧输出。

量化格式描述数字怎样编码：例如 BF16、分块 FP8、不同 FP4 或 GGUF 类型。布局描述这些编码怎样在内存排列：分组、转置、交错、scale 的位置。kernel 描述哪种硬件指令和并行算法读取这种布局完成运算。名字都带 FP4，不表示格式、布局与硬件执行能力都相同。 量化大小也不只“参数数÷2 字节”。有分组 scale、全局 scale、对齐、padding 与辅助数据。不同 kernel 还可能要求不同的 packed banks。读取 bank 时缺一组 scale 会改变数值；按错布局读则连矩阵对应关系都不对。


13.2 计算层拿到什么


OffloadMoELayer._expert_gemm 把当前 bank schema 和 views 组成 ExpertView，附上 slots 或整层 n、必要的 alphas，再调用 self.quant_method.apply。数据搬运侧负责提供可读的行，计算侧负责按 method 的布局解释这些行。因此同一套缓存控制能服务多种专家格式，而不需要缓存层手写每种 GEMM 的数学。

15.3 释放有两个层面

16.1 从一个递推式理解问题


普通 Attention 保存各位置 K/V。线性注意力或其他递归模块可以抽象为 s_t=f(s_(t−1),x_t)。只拿到 s_10，通常无法反推出 s_7；因此“前 7 个 token 没变”不意味着能把最终 s_10 裁短。如果工具调用返回内容被改写，改写点之后的旧状态就不再对应新历史。 教学旧 ids 长 10，新 ids 前 7 个相同，后缀不同；已有快照长度为 4、6、10。最近可用快照是 6，不能选 10。若新长度 9，就从位置 6 开始处理 3 个 token。即使普通 KV 能精确匹配到 7，递归层也只能从已保存的边界恢复，整个模型需要尊重这层限制。

16.3 为什么快照不能原地继续改


同一个树节点的快照可能服务多个后续请求。如果请求直接把它当活跃状态更新，后来的请求会读到被污染的历史。恢复时需要把快照复制到自己的 live slot；运行中还用 track/ping-pong 槽形成可捐赠的边界快照。快照的 lock、evict 和 live 请求槽的释放，是另一套资源账本。 HybridRadixCache 为 full KV 与 mamba snapshots 分别记录可驱逐量；可能出现节点还有路径/KV，但 snapshot 已被驱逐的情况，匹配时必须往上退。不同模型的状态 shape、dtype 和额外 slot states 由模型/状态池契约管理。

18.3 怎样理解弹性

19.1 离线 LLM 是一个更短入口


本版本 LLM 继承 Scheduler，使用 offline_mode，自己维护 pending_requests/status_map。generate 把 prompts 和 sampling_params 放入待处理列表，run_forever 运行同一调度骨架，直到 RequestAllFinished；offline_receive_msg 构造 UserMsg，offline_send_result 收集输出 token，最后 decode 为文本。 因此离线没有必要经过 HTTP、SSE 和在线 FrontendManager 的所有通道，但仍要加载模型、分配缓存、调度和执行。raw string 的离线 tokenization 也不自动等于在线 messages 的聊天模板。想做公平比较，要把最终 ids 和设置对齐。
