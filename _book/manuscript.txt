## 1.1 从一次真实困惑开始
假设模型共有 100 GiB 参数，但当前 GPU 只能给权重留下 20 GiB。我们听说 MoE 每步只激活少数专家，于是产生一个直觉：既然只用一小部分，直接加载这一小部分不就可以了吗？问题在于，**这一层会选哪些专家，要等前一层算出 hidden states、再经过 router 才知道**。下一步、下一请求还可能换一批。没有被当前 token 用到的专家，也不能永远丢掉。
FreeToken 要解决的就是这类运行时问题。它读取已经训练好的权重，把较大的专家集合保存在主存，根据执行阶段把需要的权重送到 GPU，或者直接让 CPU 计算部分专家。这里“free”不意味着数学运算或内存访问没有成本；学习这套引擎，关键是看清成本被放在哪里、何时发生、如何与其他工作重叠。
本书以官方 FlashML-org/FreeToken 的固定提交为准。它也有稠密模型、不同注意力、量化、多模态和多卡支持。为了先抓住主干，我们以**单卡、文本、MoE、普通因果注意力**讲完整请求，随后再把扩展分支接回地图。没有要求你先装好上百 GiB 权重。

## 1.3 沿箭头走一遍
用户发来 messages。前端验证参数，Tokenizer 把对话模板变成 ids。Scheduler 匹配可复用前缀、决定本次处理哪些 token，并分配写入位置。Engine 运行模型，每层先做注意力，再进入专家前馈。专家模块决定使用 GPU 中已有的权重、搬入缺失权重，或交给 CPU。最后 hidden states 经 LM head 产生 logits，Sampler 选 next id，结果提交后变成增量文本。

## 2.1 把模型缩小到能检查
这里取 N=1、D=4、E=8、top-k=2、FFN 中间维度 F=6。输入 x=[1,0,−1,2]。E 指每层可选专家数，不是所有层的专家总数。一个 route 是“一个 token 选择某个专家并带一个权重”；两个 token 都选择专家 3，就有两条 route，却只有一个需要搬运的唯一专家。
教学 router 矩阵 R 为 4×8。我们按行向量约定计算 z=xR，得到 [0.300,0.500,−0.300,1.100,−0.500,0.100,−0.300,0.600]。例如第 3 号专家（从 0 编号）的 logit 为 1×0.4+0×0−1×(−0.1)+2×0.3=1.1。
softmax 先把 logits 转为 8 个概率；选择最大的两个，对应专家 3、7。我们规定选中后再归一化，因此权重分别为 0.622459… 与 0.377541…。这等价于在这两个选中 logits 上做 softmax。本例选择这一规则是为了算清楚；真实模型还可能有 sigmoid、分组选择、bias、缩放或共享专家，必须看具体 router。
## 2.2 专家内部没有魔法
每个专家都有 Wg、Wu、Wd。按本书的行向量记法，Wg 和 Wu 是 4×6，Wd 是 6×4。先求 g=xWg、u=xWu，再求 a=SiLU(g)⊙u，最后求 ye=aWd。SiLU(t)=t/(1+exp(−t))，⊙ 表示对应元素相乘。
为了让你复算任意元素，所有权重都有定义。下列 i、j、e 都从 0 编号；脚本生成完整矩阵，不依赖随机种子。
~~~
Wg[e,i,j] = (e+1)*(i+1)*(j+1)/100
Wu[e,i,j] = (i-j+e+1)/20
Wd[e,i,j] = (j+1)*(i+1)/(50*(e+1))
~~~
专家 3 的 g=[0.240,0.480,0.720,0.960,1.200,1.440]，u=[0.600,0.500,0.400,0.300,0.200,0.100]。它的第一个中间元素是 SiLU(0.24)×0.6≈0.081。六个中间元素乘 Wd 后得到 y3≈[0.017,0.034,0.051,0.068]。专家 7 得到 y7≈[0.060,0.119,0.179,0.238]。
最终 y=0.622459…×y3+0.377541…×y7≈[0.033,0.066,0.099,0.132]。显示时保留约三位小数，后续计算始终使用完整浮点值。真实 PyTorch 权重常以输出维在前保存，kernel 还会转置或打包；矩阵物理布局不能直接套用本段的教学方向。

## 3.1 不要从名字猜入口
pyproject.toml 声明 `ft = freetoken.cli:main`。cli.main 根据第一段命令选择 runner；serve 进入 _run_serve，再调用 server.launch.launch_server。注意根目录的 freetoken/launch.py 主要负责配置并启动外部 agent；**服务进程启动应先读 server/launch.py**。把两个 launch 看成一回事，会一开始就走错调用链。

## 3.2 把进程和对象分开画
launch_server 先 parse_args，必要时解析 GPU 标识，再构造 start_subprocess 回调交给 run_api_server。回调使用 spawn，为每个 TP rank 启动 Scheduler 进程，另启动 detokenizer 和配置数量的 tokenizer workers。默认参数还会影响 tokenizer 链接方式，不能把图中的一个功能框机械地理解为永远只有一个固定进程。
单 A100 对应 TP size=1，模型执行后端只有一个 rank。FrontendManager 在 API 服务侧负责 uid、消息发送与结果队列；Scheduler 进程里包含 Scheduler 对象和 Engine 对象，后者绑定 GPU、加载模型、建立缓存与图。**一个 Engine 对象不等于一个单独的 Engine 进程**。
|边界|传递的东西|这一步不应混淆的状态|
|HTTP → 前端|JSON、连接、采样设置|网络生命周期与 GPU 生命周期不同|
|前端 → tokenizer|TokenizeMsg、uid、模板参数|原始 messages 还不是模型 ids|
|tokenizer → scheduler|UserMsg，含 ids 与采样参数|uid 用于把结果送回原请求|
|scheduler → detokenizer → 前端|next_token、finished、错误/统计|模型 token 与文本 delta 不同|
@source server/launch.py|launch_server|先看参数解析，再看 start_subprocess 中 mp.Process 的 target、name、args，最后看 run_api_server 接收回调。
@source server/launch.py|_run_scheduler|输入 ServerArgs 与 ready 队列，创建 Scheduler，成功初始化后发 ready，再进入 run_forever。
## 3.3 为什么 ready 必须晚于权重加载
端口能打开，不表示模型已经可执行。模型初始化还包括 checkpoint 读取、host bank 分配、CPU executor 建立、KV 容量计算和图捕获。上游把后端就绪确认送回 supervisor，让前端能够区分 loading、ready 和后端死亡。初学时不要用“curl 有响应”代替“后端 ready”。

## 4.1 模型结构先于数据填充
Engine 初始化会绑定设备、调整配置，并根据注册的架构构建模型。构建结构时必须知道 hidden size、层数、专家数、注意力类型和量化方案，这决定每个参数或 bank 的形状。meta-device 构造可以帮助查询布局而不真正分配整套数据；不能把它当作模型已经在 GPU 中加载完毕。
接下来需要把非专家权重与专家权重区分。前者通常在 GPU 常驻，后者在 offload 路径形成 host banks。bank 是按统一 schema 管理的一类张量集合；同一专家可能同时需要 gate_up、down、scale 等多个 bank 的对应行。拷贝了 packed weight 却忘记 scale，得到的不是正确专家。

## 4.2 物理布局是执行契约
假设教学专家有 4×6、4×6、6×4 三个矩阵。在普通浮点教学中我们分别保存；实际引擎可能把 gate 与 up 拼成一个 bank，也可能按量化分组打包、转置、交错存储。CPU executor 与 GPU kernel 必须各自知道该布局。当前版本还可处理不同层有不同专家格式的模型，因此布局检查、按 layout 分 pool 都是正确性所需。
一份逻辑专家权重的源数据与一份 GPU 副本要能对应起来：源指针确定哪一层哪一专家，目标 slot 确定写往 GPU 的哪一行，schema 确定该行包含哪些数据。后面的缓存索引只是在这份契约之上选择行。
## 4.3 pinned memory 解决什么
异步跨设备传输需要稳定、可供设备访问的主存地址。pin/lock 也有系统成本和上限：大量内存被固定后，其他任务能灵活使用的主存会减少。上游 HostBank 管理分配与 residency，装载流程可在数据到位后 pin，并支持流水处理；具体默认和回退要看硬件、格式与配置。
因此“主存足够大”和“能把所有专家以所需方式 pin 好”是两个检查。PinFailed 也不应一律解释为 GPU OOM。CPU decode、未 pin 层和 pageable 整层 prefill 有专门约束，不是任意把 non_blocking=True 改为 False 就等价。
@source moe/host_banks.py|HostBank.pin|查看注册、失败处理与 residency 更新。这里解决的是主存页和设备访问属性，不是 KV 页面分配。
## 4.4 FTW 是装载格式，不是学习算法
HF checkpoint 可能需要运行时重新组织专家参数。FTW 将 FreeToken 运行时需要的数据和元信息保存到便于读取的文件结构中，减少重复装载处理。FTWReader.read_into 的目标是把指定条目读到目标缓冲，而非训练新权重。
若 layout 或 kernel 选择变化，旧 FTW 的 packing 可能与当前方法不匹配。应读错误并重新确认转换配置。不要把“格式转换”与“模型一定变成某种量化精度”混为一谈；是否转换量化由具体转换选项和输入格式决定。
@source checkpoint/convert.py|convert_checkpoint|读取输入、输出、方法选择与已有结果校验，确认转换产物及元信息从何而来。
@source checkpoint/ftw.py|FTWReader.read_into|输入条目与目标缓冲，处理分片和读取；输出是填充后的数据，而不是模型预测。

## 5.1 先估算一个专家有多大
本书教学 SwiGLU 专家参数数为 DF+DF+FD=3DF。D=4、F=6 时只有 72 个数，BF16 占 144 字节。真实模型代入 D、F 后会很大；有 bias、scale、padding、TP 切片或不同格式时，必须按各 bank 的真实 numel×element_size 求和。源码 layer_slot_bytes 就按每层各 bank 的一行计字节，部分固定驻留 scale 另计。
普通全注意力的 KV 大致随 token 数线性增长。每个 token 的 K/V 字节数可从层数、KV head 数、head dimension 和 dtype 推出，但混合注意力、MLA、SWA、状态池不能统一套一个公式。引擎先识别 pool family，再用该类的成本模型。

## 5.3 一个直接的取舍
假设请求变长，预留 KV 从 7 GiB 提到 11 GiB，其余不变，专家预算从 20 降到 16 GiB，按同一教学 slot 可放 128 个。专家 miss 率可能升高，但更长上下文得以容纳。反之，强行保持 160 slots 可能让队列无法被接纳。
双缓冲需要容得下两层专家的暂存视图；CPU MoE 策略的 GPU 预留也不能简单理解为零专家空间。初始化配置会根据策略调整。auto 是一个规则集合，最终日志里的 Resolved config 比你只看命令行中写的 auto 更接近真实执行。
## 5.4 四种专家执行策略放在一起
|策略|专家主要保存在哪里|Prefill 的主路径|Decode 的主路径|
|fused|全部专家 GPU 常驻|GPU 专家计算|GPU 专家计算，无 offload slot 调度|
|offload|完整 host banks + GPU 部分副本|整层暂存到 GPU，可双缓冲|缺失专家搬入，选中专家都在 GPU 计算|
|cpu|完整 host banks + GPU prefill 缓冲|整层暂存，保留两层缓冲|CPU 执行专家；模型其他 GPU 主干仍照常运行|
|hybrid|完整 host banks + GPU 专家缓存|沿 offload 家族的 prefill 路径|GPU 算命中与选定 fill，CPU 算其余 miss|

## 7.2 对照真实 Req 字段
Req.input_ids 是 CPU 已保存的 ids。device_len 表示设备侧调度长度，cached_len 表示当前进度；extend_len=device_len−cached_len 给出本次尚待处理的长度。max_device_len 由初始输入和输出预算共同决定，remain_len 用来判断是否还有输出空间。它们不是五个同义词。
Req.complete_one 把 cached_len 设为当前 device_len，随后让 device_len 增 1，为下一 token 准备位置。这个方法在 Engine.forward_batch 里调用，时间上可以早于 CPU 收到采样结果。Req.append_host 才把 next token 真正追加到 CPU ids。因此在 overlap 中，`len(input_ids)` 不必时时等于 device_len。

## 7.3 本版本如何选下一批
Scheduler._schedule_next_batch 先尝试 PrefillManager，再尝试 DecodeManager。这是本提交的具体策略；源码还留有支持其他策略的 TODO。不要直接套用其他推理引擎“decode 优先”或“同一 batch 混合所有阶段”的描述。
prefill 的 token 预算、请求表、KV 和状态池共同限制接纳；长 prompt 可被分成多个 chunk。中间 chunk 还未走到完整 prompt 末尾，因此不能把每个 chunk 的最后一行都当作对用户输出一个新词。ChunkedReq 和结果处理中的分支负责这层区别。

## 8.1 从三行 ids 到三行向量
统一请求 prefill 有 N=3。教学 D=4 时，Embedding 输出 H 为 3×4，每一行对应一个输入位置。真实 Qwen3 MoE 主干在 Qwen3Model.forward 中初始化 residual，再逐层传递 x 与 residual，最后做 norm。残差融合实现把“相加”和“归一化”放进高效算子，因此不能只看到一行 layernorm 就误以为残差没了。
一个教学 Pre-Norm 层可以写成 A=Attention(Norm(H))，U=H+A，M=MoE(Norm(U))，Hnext=U+M。这段表达用于理解数学；真实 fused residual 的中间存储顺序需要对照函数接口。各层有自己的权重与 KV 存储，上一层输出行是下一层输入行，不能跳过某层直接复用别层 K/V。

## 8.2 一次 Attention 的形状
为了手算，取双头 h=2、每头 d=2、D=4，暂用 MHA。Hnorm[3,4] 分别乘 WQ/WK/WV[4,4]，得到 Q/K/V[3,4]，再看成 [3,2,2]。每头 QKᵀ 得 [3,3] 分数，缩放后施加因果 mask；位置 i 只能读不晚于 i 的位置。每行 softmax 后乘 V，得到每头 [3,2]，拼接并输出投影回 [3,4]。
真实 GQA 中 Q head 数可大于 KV head 数，K/V 形状按 KV heads 计算，多个 Q heads 共享一组 K/V。RoPE 用 positions 旋转 Q、K；它不把 token id 当位置，也不替代因果 mask。Q/K norm、SWA 和 sparse attention 是否存在由模型与 backend 配置共同决定。
## 8.3 写入位置不由 token id 决定
Scheduler 分配的 out_loc 给当前输入行指定物理写入位置。以 Triton 后端为例，forward 先 store_kv(k,v,out_loc,layer_id)，再根据 metadata 和 phase 选择 decode 或 extend kernel。因而缓存 11 号 token 的位置不是“第 11 号缓存单元”，而是这条请求当前位置对应的已分配槽。

## 8.4 Decode 改了什么
当输入 id 8 时，当前 H 只有 [1,4]，Q/K/V 只有新位置的行；每层 Attention 用新 Q 读取该层已有 K/V，并加入新 K/V。过去 token 的前馈和投影通常不再重复执行，代价转为读取历史状态。输出仍为 [1,4]，继续进入同一层 MoE，再进入下一层。不是只跑最后一层，也不是只运行 router。
@check 第 5 层能用第 4 层的 KV 代替自己的历史 KV 吗？|普通 Transformer 不能。两层权重不同、表示不同，缓存按层组织。这里不讨论另外设计的跨层共享模型。

## 9.1 长 prompt 与短 decode 的差别
一个 token 只选 2 个专家，但 1000 个 token 的选择并集可能覆盖大部分 E。若每层等 router 完成后才逐个收集缺失专家，可能既搬了大量数据又增加启动与同步开销。prefill 还有较多输入行，可把专家 GEMM 做得更大；用当前层计算时间遮住下一层权重传输就更有机会。
在本提交的 offload prefill 路径，_prefill_routed 使用整层 materialization。开启 prefill_overlap 时，通过 _wait_prefill_overlap 调用 begin_prefill、预取当前层和下一层、等待当前层 ready，然后计算。关闭 overlap 时也有同步 materialize_layer 路径。**这里的回退不是自动变成 decode 式按需 top-k 搬运**。

## 9.2 缓冲 A/B 必须有读写协议
令偶数层使用缓冲 0，奇数层使用缓冲 1。计算层 0 时可搬层 1；层 2 再使用缓冲 0，但必须等层 0 的 GPU 读取结束。ready 事件表示拷贝完成，release 事件表示计算不再读该缓冲。它们方向相反，少任何一条依赖都可能把正在被 GEMM 读取的权重覆盖。
begin_prefill 还要把新的拷贝工作排在先前 decode 后面。因为暂存区借用 GPU bank 空间，上一批 decode 也可能正在读那些字节。Python 函数返回“已经发起异步复制”，不等于旧读取已经结束。

## 10.1 两个编号空间
专家编号表达模型语义，slot 编号表达物理存放位置。完整专家身份是 (layer,e)，因为不同层的 expert 3 不是同一组参数。扁平 key 可写成 layer×E+e，但 GPU pool 里的 slot 只编号当前物理行。让 topk_ids 从 expert id 变为 slot id，是把逻辑路由接到物理缓存的关键一步。
缓存同时维护正向 slot_for_id 和反向 id_of_slot，配合 usage/step。新专家写到某个 slot 时，必须清掉旧专家的正向映射；否则下次“命中”会拿到已经被覆盖的字节。这个错误通常不会表现为崩溃，而会表现为错误答案。

## 11.1 先把集合写清楚
令 H 为命中的唯一专家，M 为缺失的唯一专家。把 M 分成 F 与 C：F 被搬到 GPU，C 在 CPU 原地计算。GPU 最终处理 H∪F，CPU 处理 C。它们必须不重不漏。q=|F|，m=|M|；别把 m 错写成 batch_size×top_k，那是 route 数上限，去重后可能小很多。
为什么要保留 fill？本步 CPU 可以算完一个缺失专家，但若它以后常被选中，搬到 GPU 会让后续命中。反过来，一口气填满所有 miss 又可能被 PCIe 限制。因此这是本步关键路径与后续驻留的共同问题；本章的带宽模型只解决其中的时间分工。
## 11.2 用同一单位推时间
先采用简化模型：单专家 S 字节；有效 H2D 带宽 BP；主存侧总有效带宽 BH，且 BH>BP。若 DMA 与 CPU 争用主存，简化地把并发 CPU 剩余带宽记为 BH−BP。于是 fill 时间约 qS/BP，CPU 时间约 (m−q)S/(BH−BP)。两边重叠时较慢的一边决定结束时刻，因此应比较 max，而不是把两个时间相加。
令两项相等，q(BH−BP)=(m−q)BP，得到 q*=mBP/BH。它依赖一系列假设：均匀专家大小、可重叠、忽略启动固定成本、CPU 计算可用带宽描述。若 BH≤BP，这个剩余带宽写法不再适用；也不应拿厂商标称值代替本机有效值。
教学例子 m=8、S=64 MiB、BP=20 GB/s、BH=80 GB/s，q*=2。fill 两专家约 6.711 ms；CPU 六专家在 60 GB/s 下也约 6.711 ms。表中 GB/s 是十进制字节带宽，MiB 是 2²⁰ 字节，换算不能混掉。

## 12.1 一个具体分区
假设本层两条 route 是专家 3 和 7，3 已命中，7 分给 CPU。GPU 获得 slot(3) 和原权重 w3；CPU 那条 route 在 GPU 的权重置 0，slot 置 −1 或安全的 0。CPU 获得 expert id 7 和原权重 w7；专家 3 那条 route 的 cpu_id 为 −1。CPU 内核跳过负编号。
若某个 GPU kernel 不支持跳过 −1，单把权重设 0 还不够：它可能仍然先读取 slot 内容。源码用 clamp 和可安全读取的 storage 约束这条路径，避免越界或 0×NaN。优化的正确性往往就藏在这些“即使权重为零也会读”的细节里。

## 12.3 为什么需要常驻线程与握手
每个 token 每层都临时创建线程的代价太高。CpuMoeExecutor 初始化原生扩展和线程池，并让输入、输出、描述符与信号具有稳定地址。CPU 指令集、线程数、亲和性和 NUMA 会影响有效吞吐；A100 并不能告诉我们配套 CPU 的主存带宽。
当前实现根据探测结果使用 flag publish/signal/wait、kernel I/O 或 host function 等路径。CUDA Graph 兼容性取决于这一协议是否可重放；探测不支持时，代码可能要求禁用图，而不是默默产生旧结果。Engine 每次 forward 还检查 executor 健康状态，避免 CPU 协调线程失效却继续用陈旧输出。
## 12.4 怎样证明没有漏算

## 13.1 三个层次别混掉
量化格式描述数字怎样编码：例如 BF16、分块 FP8、不同 FP4 或 GGUF 类型。布局描述这些编码怎样在内存排列：分组、转置、交错、scale 的位置。kernel 描述哪种硬件指令和并行算法读取这种布局完成运算。名字都带 FP4，不表示格式、布局与硬件执行能力都相同。
量化大小也不只“参数数÷2 字节”。有分组 scale、全局 scale、对齐、padding 与辅助数据。不同 kernel 还可能要求不同的 packed banks。读取 bank 时缺一组 scale 会改变数值；按错布局读则连矩阵对应关系都不对。
## 13.2 计算层拿到什么

## 14.1 固定的是执行结构，不是输入数值
CUDA Graph 记录一组设备操作及其依赖。输入、输出地址需要稳定，但其中的数值每步可以更新。若缓存命中判断、miss 数量、src/dst 索引由设备端计算并放在固定缓冲中，后续操作根据设备端 count 工作，就能在固定形状的图中处理变化。
相反，在 Python 中 `.item()` 读 miss 数、临时创建任意长数组再发不同操作，会把动态决策拉回主机，增加同步并妨碍捕获。理解这点比背“CUDA Graph 更快”重要：它解释了 offload cache 为什么有固定尺寸索引和 device count。

## 14.3 CPU 分支也有捕获条件
CPU executor 的稳定 pinned I/O 和信号地址让 CPU 读到这一轮的真实激活与路由。发布、等待和结果合并必须组成可重放协议。当前代码不只依赖一种 host node，且在运行时检查 graph capture safe。不能承诺“任何 CPU 扩展都能放进图”。
还要注意 stream 间的数据竞争。Scheduler 准备下一 batch 时可能改页表，而旧图仍在运行；某些后端必须在回放前快照元数据，避免下一轮改表影响在途读取。优化省掉的不是所有同步，而是保留必要依赖、减少不必要的主机往返。

## 15.1 一页不是一个专家
专家 slot 保存权重；KV page 保存过去 token 的中间状态。前者按 (layer,expert) 识别，后者与某条精确输入前缀及位置有关。两种缓存都叫 cache，但 key、数据、来源和寿命不同。把 KV 命中率当专家命中率，性能分析就会得出错误结论。
普通分页教学取 page_size=4，逻辑 page table=[7,2,9]。位置 p=5 的逻辑页为 1，页内偏移 1，对应物理页 2，线性 slot=2×4+1=9。模型仍认为它在位置 5，RoPE 使用 5；物理 slot 9 只影响存取地址。源码 Context.page_table 的展开方式与本教学小表不完全相同，具体应沿 _write_page_table 查看。

## 15.2 Radix tree 保存什么
RadixPrefixCache 按 token 前缀压缩路径，节点关联对应 KV 索引。新请求的 ids 从根匹配，直到某个 token 不同；匹配长度可能受页对齐等约束。匹配到的状态需要 lock，防止运行时被驱逐；请求不再使用后 unlock，之后可以作为可驱逐的可复用状态保留。
CacheManager.match_req 特意最多匹配到 input_len−1，因为只保存 KV 不等于保存末尾采样所需 logits。即使 prompt 完全重复，仍可能需要处理最后位置来得到输出分布。前缀缓存和“整条请求结果缓存”不同。

## 15.3 释放有两个层面
活动请求结束，需要释放请求表和活动引用。一部分 KV 可插入 prefix cache，继续占物理页，等待下次精确前缀命中；容量紧张时再驱逐。这不是自然等同于泄漏。判断泄漏要看无法回收的孤立分配、引用计数不平衡或容量账本不一致，而不只是看显存使用没立即下降。
SWA 只需保存窗口相关状态；MLA、压缩/稀疏注意力使用专有 geometry；混合递归模型还需快照。引擎通过 pool family 与 cache manager 分支处理这些差别，不能所有模型都套“所有层 K,V 各一张完整历史表”。
@check 两个语义相似但 token ids 不同的 prompt，会自动共享所有前缀 KV 吗？|不会。这里匹配精确 token 前缀，不是向量相似度搜索；不相同的历史状态不能随意互换。
@check 位置 p=4、P=4、table=[7,2,9] 时应写到哪？|逻辑页 1、偏移 0、物理页 2、线性 slot 8。位置编码仍是 4。

## 16.1 从一个递推式理解问题
普通 Attention 保存各位置 K/V。线性注意力或其他递归模块可以抽象为 s_t=f(s_(t−1),x_t)。只拿到 s_10，通常无法反推出 s_7；因此“前 7 个 token 没变”不意味着能把最终 s_10 裁短。如果工具调用返回内容被改写，改写点之后的旧状态就不再对应新历史。
教学旧 ids 长 10，新 ids 前 7 个相同，后缀不同；已有快照长度为 4、6、10。最近可用快照是 6，不能选 10。若新长度 9，就从位置 6 开始处理 3 个 token。即使普通 KV 能精确匹配到 7，递归层也只能从已保存的边界恢复，整个模型需要尊重这层限制。

## 16.2 “语义锚点”的语义在哪里
锚点可能安排在工具调用等结构边界，这种位置更可能在后续历史编辑中保留。它不是把不同文字按语义相似度映射到同一个状态；正确性仍要求边界前的精确 token 历史一致。边界位置、特殊 token 检测和 chunk/page 对齐也必须满足实现条件。
当前 CacheManager.snapshot_toolcall_anchor 会检查 hybrid 模式、anchor、ping-pong 槽、cached_len 恰好到边界及页对齐，然后在 engine stream 上复制状态。结果提交发现 tool-call opener，记录的是边界长度；**不能在采样刚得到 opener 的瞬间就认为它的输入计算已经完成**。第 7 章的“已知/已计算”差别在这里再次出现。

## 16.3 为什么快照不能原地继续改
同一个树节点的快照可能服务多个后续请求。如果请求直接把它当活跃状态更新，后来的请求会读到被污染的历史。恢复时需要把快照复制到自己的 live slot；运行中还用 track/ping-pong 槽形成可捐赠的边界快照。快照的 lock、evict 和 live 请求槽的释放，是另一套资源账本。
HybridRadixCache 为 full KV 与 mamba snapshots 分别记录可驱逐量；可能出现节点还有路径/KV，但 snapshot 已被驱逐的情况，匹配时必须往上退。不同模型的状态 shape、dtype 和额外 slot states 由模型/状态池契约管理。
@source kvcache/linear_state_pool.py|LinearStatePool.copy_from|看状态复制的范围，理解“恢复一个请求”不是复制一个抽象整数编号。
@source scheduler/scheduler.py|Scheduler._restore_linear_states|查看恢复发生的 stream 和调用时机。它必须排在读 live state 的前向之前。
@check 最长 token 前缀命中 7，但最近 live snapshot 在 6，应从哪恢复？|从 6。不能假装有长度 7 的递归快照；KV 匹配量与模型整体可恢复量可能不同。
@check 工具边界的特殊 token 刚被采样出来，状态快照就一定包含该 token 吗？|不是。它要在后续作为输入完成计算后，cached_len 才达到对应边界。代码按这个时机冻结状态。

## 17.1 LM head 不是 tokenizer.decode
模型末尾 hidden states 经词表投影产生 logits。prefill 有多个输入行，但生成只需要各请求最后有效位置对应的分布；后端元数据与 LM head 共同完成这层选择。decode 每个真实请求通常只贡献一个当前行。最后的 logits 形状按真实输出请求组织，而非把每个 prompt 位置都送给用户。
Sampler.prepare 为 batch 构造温度、top-k/top-p、greedy mask 和 penalties。Sampler.sample 在纯 greedy 情况直接 argmax；混合采样批次也为 greedy 行显式选 argmax，避免把近零温度当成严格 greedy 的替代。路由 top-k 与这里词表采样 top-k 是两个不同空间。
@source layers/embedding.py|ParallelLMHead.forward|prefill 先用 metadata.get_last_indices 选每请求最后有效行，再做词表投影。多卡路径还要收集分片词表 logits。
@source engine/sample.py|Sampler.prepare|读每条请求如何产生 batch 参数，注意 penalties 的输出 token 计数与 overlap 的关系。
@source engine/sample.py|Sampler.sample|标出 argmax、概率采样、混合 greedy mask 与输出计数更新。它返回 token ids，还没有返回中文文本。
## 17.2 异步结果怎样安全提交
Engine.forward_batch 返回 next_tokens_gpu、next_tokens_cpu、copy_done_event。Scheduler._forward 把 GPU ids 写到 token_pool；_process_last_data 等 copy_done，再 append_host，依次判断 EOS、输出预算、stop strings，构造 DetokenizeMsg，并释放结束请求的活动资源。
默认 overlap 可能在处理上一轮停止条件前已经排了下一轮。代码用 finished_reqs 等保护，避免向已终止用户继续发送多余 token 或二次释放。教学串行轨迹只表示必要的逻辑前向次数，不承诺真实时间线中永远没有被提前排入的计算。

## 17.4 用户断线也会改变资源寿命

## 18.1 容量背后有真实地址

## 18.3 怎样理解弹性

## 19.1 离线 LLM 是一个更短入口
本版本 LLM 继承 Scheduler，使用 offline_mode，自己维护 pending_requests/status_map。generate 把 prompts 和 sampling_params 放入待处理列表，run_forever 运行同一调度骨架，直到 RequestAllFinished；offline_receive_msg 构造 UserMsg，offline_send_result 收集输出 token，最后 decode 为文本。
因此离线没有必要经过 HTTP、SSE 和在线 FrontendManager 的所有通道，但仍要加载模型、分配缓存、调度和执行。raw string 的离线 tokenization 也不自动等于在线 messages 的聊天模板。想做公平比较，要把最终 ids 和设置对齐。

## 19.2 多模态增加一条编码支路
图像先由 processor 处理并替换 prompt 中相关占位区间，产生 mm_items 和可能的 mRoPE 位置。Scheduler 规划当前 chunk 的 encoder jobs、gather plan 和行映射；Engine._run_mm_encoder 运行/复用编码结果，再把视觉 embedding 合入语言模型输入。
因此图片不是先完整“变成一句描述”再送入文本 tokenizer，也不是所有模型的图像位置都只用一个普通一维位置整数。不同模型的 image span、双向注意力规则与编码器生命周期要看相应架构。

## 19.3 多卡增加通信与一致性约束
TP 把部分权重和计算分在多个 rank。线性投影、head 切片、专家中间维、collective 等需要一致的分片规则；有些数据可复制，有些要 all_reduce/all_gather。层中 _maybe_all_reduce 提示本地专家输出还可能需要跨 rank 合并。本书单 A100 实验固定 TP=1，不能据此声称已经验证多卡正确性。

## 19.4 运行管理不等于模型前向
daemon 管理服务进程、状态、切换与恢复；shell 提供交互；ft launch 帮外部客户端配置 provider；它们最终围绕同一个模型服务工作。它们的重要性在部署生命周期，不在把一个 expert 矩阵乘快。阅读时先按“谁创建/监督谁”定位，再回到每 token 执行路径。

## 20.4 第四阶段：先验证一条请求
选择官方 models.md 列出的、host RAM 与显存均能容纳必要部分的 MoE checkpoint。首次优先使用当前环境确实支持的 BF16/FP8 路径，避开未核实的 NVFP4 特定快速路径。下面的 MODEL_PATH 必须换成你实际已下载的兼容模型；不预设 A100 是 40G 还是 80G，也不默认你有几百 GiB RAM。
~~~
export MODEL_PATH=/absolute/path/to/your-supported-moe-checkpoint
ft serve --model "$MODEL_PATH" --moe-strategy offload \
  --attention-backend triton --max-running-requests 1 \
  --cuda-graph-max-bs 0 2>&1 | tee offload-eager.log
~~~
另一终端进入教材目录，运行本书的 HTTP 客户端。它查询 /v1/models 得到真实 model id，发送固定请求，保存原始 SSE 与可见内容事件的到达时间。
~~~
python labs/http_probe.py --out offload-eager.json
~~~
验收：服务日志 ready；Resolved config 是预期 offload/attention；请求能结束；JSON 含 model、usage、内容事件和总时延，无 error。客户端记录的是应用侧时间，content event 也不保证一事件一 token，不能直接当 GPU ITL。先用短输出核对模型可工作，再固定较长输出用于稳定测量。
## 20.5 第五阶段：一次只改变一个因素
完成基线后，先停止当前实验服务，再用相同 checkpoint、prompt、输出预算、temperature、KV 预算与 CPU 线程设置逐项改变。启用图时只改图设置；比较 hybrid 时先测 bandwidth 并核对 profile 行命中，再改 moe-strategy；比较 prefill overlap 时只改对应开关。每种配置先独立记录冷启动/首请求，再预热后至少测 5 次，报告中位数与范围。
~~~
ft bench bw --model "$MODEL_PATH"

# Use the same serve flags as the baseline, changing only this strategy:
# --moe-strategy hybrid
# For graph A/B, change only --cuda-graph-max-bs 0 to 1.
# For prefill A/B, add only --disable-moe-prefill-overlap.
~~~
记录实际 expert slots、KV pages、CPU 线程、有效带宽、命中/搬运统计（若启用）、prompt/output 实际 token 数、应用侧首内容时间与总时延。短输出可能只测到固定开销；仅对比一条文本不足以确定优化有效。

## 21.1 第一张表：前向之前
|顺序|调用位置|输入 → 输出|状态变化|
|1|协议 handler / submit_generation|messages → 生成描述与 TokenizeMsg|前端登记 uid 与回复通道|
|2|TokenizeManager.tokenize|模板文本 → CPU int32 ids|生成 UserMsg，真实长度确定|
|3|Scheduler._process_one_msg / PrefillManager|UserMsg → 等待请求与可执行 Req|匹配前缀、保留必要资源|
|4|_schedule_next_batch / _prepare_batch|Req 集合 → ForwardInput|分配页、positions、out_loc、元数据和采样设置|
本书 ids=[11,10,7] 是第 2 步之后的教学替身。它跳过真实模板编号，却没有跳过后续调度和缓存所需的长度关系。若你要用真实模型替换它，先运行实际 tokenizer，重新记录 ids 与 special tokens。
## 21.2 第二张表：一次模型执行
|顺序|处理|主要形状/身份|必须保留的对应关系|
|5|Embedding|N → N×D|每一行对应请求位置|
|6|每层 Norm、QKV、RoPE、Attention|N×D → N×D|本层历史状态、position 与 out_loc|
|7|router|N×D → N×E → N×k|专家逻辑身份、route 权重|
|8|prefill 或 decode 专家路径|整层视图或 slot 视图|bank 布局与索引空间必须一致|
|9|hybrid（若使用）|H∪F 与 C 部分和|每条 route 恰好被算一次|
|10|残差、下一层、最终 norm/LM head|hidden → 每请求词表 logits|取最后有效位置，不混 padding 行|
对于“鱼”这一轮 decode，N=1 而不是重算四个 token；但仍须经过每一层。专家集合每层都可能不同，缓存驻留跨层变化。图回放也仍执行这些数学操作，只减少主机发起成本。
## 21.3 第三张表：前向之后
|顺序|处理|产生什么|为什么不能省|
|11|Sampler.sample|next token GPU ids|logits 不是文本|
|12|GPU token_pool 写入、异步 D2H|next_tokens_cpu 与 copy_done|下一步设备输入与 CPU 结果同步|
|13|_process_last_data|host ids、终止判定、DetokenizeMsg|不读未复制完成的数据，不重复终止|
|14|Detokenizer / 协议适配|安全文本增量、usage、finish reason|字符边界、stop 与工具事件正确|
|15|资源释放/缓存保留|活动引用归还、可复用前缀保留|结束请求与保留缓存寿命不同|
普通教学串行路径必要前向两次：prefill 选“鱼”，decode 输入“鱼”选 EOS。默认重叠调度可提前排入额外一步；看性能或状态快照时要以源码时序与实际 trace 为准。若只背两次前向而忽略在途状态，就无法解释取消与二次释放保护。
## 21.4 用症状反查层次
|症状|先看什么|暂时不要下的结论|
|首请求非常慢|权重/JIT/图捕获/首次分配与冷缓存|直接说 decode 算法慢|
|长 prompt 慢|prefill 实际行数、专家搬运和 overlap|只看单 token 带宽|
|hybrid 比 offload 慢|CPU/NUMA/profile 行/线程、真实分区和同步|把 GPU 型号当全部机器能力|
|重复 prompt 仍计算末 token|match_req 截断、logits 与状态快照边界|立即判定缓存坏了|
|关闭图正常、启用图错误|地址、metadata 快照、CPU 协议与 padding|只改温度或 prompt 掩盖问题|
|结束后仍占显存|prefix cache、expert residency、图内存池|直接把所有驻留叫泄漏|
@check 请口述“router 的 expert id 怎么最后变成用户看到的一个字”。|expert id 选择专家 → cache 映射/分区 → bank GEMM 与加权和 → 后续层与 LM head → token id 采样 → 结果提交 → tokenizer 增量解码。expert id 本身不会直接变成汉字。

## 22.1 三条精读路线
第一条是请求路线：cli._run_serve → server.launch.launch_server → 前端共享生成接口 → TokenizeManager → Scheduler → Engine.forward_batch → Sampler → _process_last_data → DetokenizeManager。目标是给每条消息标 uid、方向、输入和结束条件。
第二条是专家路线：Qwen3MoeMLP.forward → OffloadMoELayer.forward → prefill/decode 分支 → OffloadMoeCache → offload_kernels/flashlib → copy_missing → quant_method.apply；hybrid 另接 CpuMoeExecutor。目标是区分原始 expert id、pool slot、route 权重、src/dst indices 和 device count。
第三条是状态路线：CacheManager.match_req → prefix cache → allocate_paged/_write_page_table → backend store_kv/read → cache_req/free；hybrid radix 再接 LinearStatePool 和 restore/snapshot。目标是说清楚每一页/槽是谁拥有、何时能驱逐、为何必须在特定 stream 上复制。
## 22.2 术语对照
|术语|本书中的准确含义|容易混淆的对象|
|route|一个 token 对一个专家的选择与权重|唯一专家集合|
|expert id|某一层内的逻辑专家编号|GPU slot id、token id|
|bank|专家某类权重/scale 的组织存储|KV page|
|pool/slot|兼容专家布局的一组物理槽及其中一行|模型的一层或一个 token|
|fill/fetch|把缺失专家权重复制进 GPU|CPU 原地执行 miss|
|prefill|处理未计算的提示位置，可能切块|模型训练、一次只输出一个用户词|
|decode|通常每请求处理一个新输入位置|只执行 LM head|
|prefix cache|精确 token 前缀对应状态复用|完整答案缓存、语义检索|
|anchor|适合恢复的结构边界状态快照|相似句子共用状态|
|CUDA Graph|稳定地址/依赖上的设备操作回放|写死每一步路由结果|
|overlap|有明确依赖的工作在时间上重叠|取消所有同步或所有阶段混批|
## 22.3 主要依据与范围
主要源码是 [FreeToken 官方固定提交](https://github.com/FlashML-org/FreeToken/tree/e4f69d9e232448fc168389c29f6f9364869cff35)。本书采集了 python/freetoken、tests、docs、benchmarks 中符合采集条件的文件和根目录必要文件，共 777 个，逐文件核对 Git blob 身份，并保存 SHA256。网页只生成直接引用及必要文档的源码阅读页；完整已采集文件在 _source 下。它不是完整可安装克隆，更没有把外部依赖源码都包含进来。
官方设计论文可见 [FreeToken 论文](https://arxiv.org/abs/2608.16157)。阅读论文适合建立设计动机，核对本提交则以函数为准。例如本书明确说明普通缓存委托 flashlib、按布局分 pool、动态 fetch 可能为 0、并发带宽优先，以及整层 prefill 暂存等具体实现条件。没有将论文图表当作本机复现结果。
叙事组织参考用户指定的 [MiniMind 第 1 章：LLM 全景与项目导览](https://tutorial.baimuyuan.online/minimind-tutorial/chapters/01-LLM%E5%85%A8%E6%99%AF%E4%B8%8E%E9%A1%B9%E7%9B%AE%E5%AF%BC%E8%A7%88)。本书采用从问题、代码地图到逐步实战的阅读组织，正文、例子和 SVG 另行编写，不复制其对 MiniMind 训练流程的叙述，也不把训练教程的结论移植到推理引擎。
